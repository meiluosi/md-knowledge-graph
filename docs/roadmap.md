# 价值与演进方向

这份文档回答三个问题：**这个项目为什么值得存在**、**接下来往哪走**、以及**什么时候算做完**。

判断"该不该做"的筛子见 [`when-to-build-a-tool.md`](./when-to-build-a-tool.md)——
下面每个演进方向都标注了它服务筛子的哪一条，避免"因为能做所以做"。

---

## 零、完工定义与停止规则

先说最重要的：**这个项目的终点不在代码里，在采纳里。**

继续加功能无法抵达终点，只能推迟它。

### 为什么工具项目永远做不完

因为**每一个新功能都能论证出合理性**——而这和"值得做"是两件完全不同的事。

所以停下来的判据不能是"还想不想做"，只能是筛子里那两条：

- 它减少哪一类**静默错误**？
- 它提高多少**被调用频率**？

**两条都答不出来，就是"因为能做所以做"。**

### 完工的定义

以下四条全部成立，就算完工：

| | 条件 | 状态 |
|---|---|---|
| 1 | 检查项覆盖了真实语料上出现过的全部静默失效类型 | ✅ 断链 / 失效锚点 / 本地路径 / 缺失图片 / 标签不一致 / 长尾标签 / 孤立节点 |
| 2 | 接入不需要勇气（基线 + 多条集成路径） | ✅ Action / pre-commit / 一条命令 |
| 3 | **有外部使用者把它挂进 CI，并且第二个季度还没删掉** | ⬜ **未成立** |
| 4 | 文档能让别人不问你就用起来 | ✅ |

**第 3 条是唯一没成立的，而它不靠写代码达成。**

一个比喻：**烟感器已经装好了，也测过不会误报。剩下的是——得有人真的住进这间屋子。**
继续提升烟感器的灵敏度，并不能让屋子有人住。

### 停止规则

**再发一个版本（v0.7.0，只含 A5 规则可配置），然后宣布功能冻结。**

冻结之后：

- 只修 bug，不加功能
- 每个新功能请求先问：它对应哪一类静默错误？
- 除非有人真的在用并且提出，否则不动

### 两种结局，都要接受

**结局一：有人用** → 路线改由用户的 issue 决定，不再由我们设想。

**结局二：一段时间没人用** → **承认它是"为我自己写的工具"，把 README 的定位改诚实，然后停下。**

第二种不是失败。它的产出仍然真实存在：

- 一个真的在用的工具（自己的博客）
- 一套可复用的判据（[`when-to-build-a-tool.md`](./when-to-build-a-tool.md)）
- 一份真实的踩坑记录（[`what-didnt-work.md`](./what-didnt-work.md)）
- 一次真实的语料验证（[`case-study.md`](./case-study.md)）

**一个诚实的个人工具，比一个假装通用但没人用的工具，更有说服力。**

### 不设终点会怎样

会一直做下去，而且每一步都"有理由"。结果是一个功能很多、每样都不深、没人用的项目——
**那是最坏的结果，因为它消耗时间却不产生采纳，也不产生可信度。**

## 一、价值

### 1. 它守的失效是静默的

这不是判断，是实测结果。把这件事从头做过一遍，踩到的四个错**没有一个会崩溃**：

| 自己写的版本会怎么错 | 错误形态 |
|---|---|
| 手写 frontmatter 解析 | `tags: [A, B]` 与 `tags: A` 解析成 `[]`，**不报错** |
| 同名异写建节点 | 生成两个 **id 相同**的节点，图畸形但**能跑** |
| wikilink 解析 | 实现了、有测试，**实际一条边都没产生** |
| 代码块里的示例链接 | 全部报成断链，一篇文章十几条假错误 |

所以这个工具的价值可以精确写成一句话：

> **把一类静默错误，转变成一条明确的、非零的退出码。**

注意它**不是**"帮你检查 markdown"——那种说法没有说明"没有它的时候，代价是什么"。

### 2. 决定工具生死的是误报与历史债，不是检出能力

这一条容易被忽略，但它比功能更能解释"为什么很多检查工具最后都被关掉了"：

- **误报**：一开就红，用户发现里面有两条是假问题，然后不再信任它
- **历史债**：接入既有项目，第一次跑出 40 个错误，用户直接把这一步从 CI 里删掉

两者都会让调用频率归零。所以本项目有两条硬设计：

- **宁可漏报，不可误报**——链接目标同名时判为断链，绝不猜一个
- **基线机制**——只对新增问题失败，历史债冻结但不阻塞

**这两条不是功能，是生存条件。**

### 3. 定位来自一个趋势，不是一个想法

规格驱动开发把 markdown 从「产物」变成了「接口」：需求、设计、任务清单、`AGENTS.md` 都是 agent 的输入。它是程序的一部分，而程序的一部分应当有和代码同等的完整性保障——代码有 `tsc`、`eslint`，markdown 什么都没有。

这个趋势改变了**失效的形态**：

| | 博客 | 规格文档 |
|---|---|---|
| 关系 | 引用另一篇文章 | **引用另一个文件的某个章节** |
| 典型失效 | 标签拼写不一致 | **章节改名，引用还指着旧锚点** |

"失效锚点"这个检查项不是想出来的功能，是从这个判断里推出来的。文件存在、章节没了——**没有任何东西会报**。

### 4. 空隙是真实的，但很窄

调研结论（见 README 的对比表）：分项都有强手，交集是空的。

- 图谱：Obsidian / Logseq / Foam / Quartz——都是**应用或站点生成器**，你得迁进去，而且拿不到数据
- 链接检查：lychee / linkinator——验的是"链接能不能打开"，不是"引用还在不在"
- 相关文章：Hugo `.Related` / Jekyll 插件——**绑死框架**
- wikilink 解析：remark 生态——只是库

npm 上搜 `markdown knowledge graph`、`related posts markdown tags` 等，**没有直接竞品**。

但要诚实：**窄定位意味着窄受众。** 这不是一个会变成大众工具的项目。

### 5. 它自己是一个可复现的工程样本

这一点对"研究工程风"的目标而言，可能比工具本身更值钱：

- [`what-didnt-work.md`](./what-didnt-work.md) 记录了 8 个真实踩坑，含四次错误的测试断言
- 依赖取舍写明了理由（为什么引 `gray-matter`、为什么引 `github-slugger`、为什么砍掉自研解析器）
- 每一个"不做什么"都写在已知取舍里

**一个项目的可信度，很大程度来自它敢写多少自己的失败。**

### 6. 诚实边界

- 目前 **0 star、0 外部使用者**。文档不能替代采纳。
- 交互式可视化已经放弃竞争——那条路必败，且不在筛子里。
- 它不会成为大众工具。**它的价值验证只有一个方式：有人真的把它挂进 CI，并且第二个季度还没删掉。**

## 二、演进方向

### A. 已有明确依据的

**A1. 行号定位** ✅ 已完成

GitHub 注解现在定位到**文件 + 行 + 列**，文本报告也用 `file:line` 形式。

修法就是把 `stripCode`（**删除**代码块，改变偏移）换成 `maskCode`（**等长空白遮蔽**，偏移不变）。偏移不变，行列就能准确还原。

**过程中先撞了一次坑**：第一版报的是**正文行号**（frontmatter 之后算起），而注解的 `line=` 是相对整个文件的——33 篇的语料上每条会偏 6 行。**错的行号比没有行号更糟**，因为人真的会去改那个位置。

**A2. 基线自动清理** ✅ 已完成

`--prune-baseline <file>`：只删除已不再出现的条目，**绝不添加**。

与 `--update-baseline` 的区别是刻意的，两者危险程度完全不同：

| | 会添加新问题吗 | 语义 |
|---|---|---|
| `--update-baseline` | **会** | 「把所有现存问题都接受为已知」 |
| `--prune-baseline` | **不会** | 「忘掉已经修好的，但绝不放过新的」 |

前者方便（一次接住全部历史债），但跑在不该跑的时候会静默接受新引入的问题。后者是日常维护动作，**它的安全性不依赖于"你记得它只在什么时候跑"**。

**A3. 图片与本地路径检查** ✅ 已完成（真实语料验证带出来的）

原本不在计划里，是[真实语料验证](./case-study.md)撞出来的：

- `C:` 被当成 URL 协议 → 19 个 Windows 本地路径引用被静默跳过
- 那 19 条全是图片，而图片原先完全不检查

现在新增 `local-file-path` 与 `broken-image` 两个检查项，以及 `--asset-root`（站点绝对路径需要用户指定资源根目录才能判断）。

**A4. 支持没有 frontmatter 的语料** ✅ 已完成（这是前提，不是新功能）

**这一条差点让整个定位变成假的。**

在回答"演进到什么时候算完"时顺手用工具检查它自己的 `docs/`，结果：

```
错误：在 .../docs 里没有找到带 title 的 markdown 文件。
```

工具**无法在纯 markdown 上运行**。而规格文档（`design.md` / `tasks.md` / `requirements.md`）**通常没有 frontmatter**——也就是说，它无法服务 README 里声称的、作为存在理由的那个场景。

现在的行为：

- 标题按 `frontmatter.title → 第一个 H1 → 文件名` 兜底
- 没有 frontmatter 的语料**不会**产生逐篇的「无标签」噪声（它们本来就不用标签）
- `missing-title` 的含义收窄为「写了 frontmatter 却没给 title」——那是笔误，值得提醒

**这一条说明什么**：它不满足"功能请求"的形态（没人提过），而是**一个让既有宣称成立的前提**。冻结功能之前必须先确认前提成立，否则冻的是一个跑不到目标场景的工具。

现在它检查自己的 `docs/`：**4 篇文章、4 条互相引用的边、0 错误 0 警告**，并且这一步进了 CI。

**A5. 规则可配置** — 服务条件 ④

检查项现在有 10 条。用户要么全开，要么全关。

补 `mdkg.config.json`：逐条启用/禁用、调阈值、改必填字段。理由和基线一样——**不能只让用户在"全红"和"关掉"之间二选一。**

随着检查项增加，这一条的必要性在上升。

**A6. 外部链接检查（opt-in）** — 不做

现在是明确的不做项（不发起网络请求）。lychee 那一类工具做得更好；加进来只会稀释定位。

### B. 由 spec 驱动趋势推出的（功能冻结后不做，除非有人提出）

**B1. frontmatter schema 校验** — 服务条件 ②

规格文件通常要求必填字段（`status`、`owner`、`implements`…）。字段缺失是**典型静默失效**：文档照样渲染，只是流程读不到。

**但它暂缓。** 理由是条件 ①：只有 spec 仓库需要它，而**至今没有任何人提出过这个需求**。"我能想到有人会需要"不等于"有人需要"。

**B2. 依赖图输出** — 不做

原本的想法是输出 `--format deps`（或 GraphML），让"`tasks.md` 引用了哪些 `design.md` 章节"能被别的工具消费。

**不做。** 因为**没有消费者**。产出一个没人读的数据格式不是价值，只是维护负担。

**B3. 增量与性能** — 不做（等有人报慢）

33 篇 / 19,673 行跑 **0.064 秒**。真正的规模问题要等到几千篇才会出现。

**现在不做。** 等到有人真的报"慢"再优化——那时才知道瓶颈在哪，而不是现在猜。

### C. 采纳层

**C1. GitHub Marketplace 上架** ✅ 做

`action.yml` 已带 `branding`，技术上合规。成本低，且**直接改善条件 ③**（被发现）。需要你在 create release 页面手动勾选——网页操作，API 做不了。

**C2. npm 发布** ❌ 不做

越过早发布意味着为一个没人用的包承担维护承诺（语义化版本、破坏性变更通知）。**等有人真的 `npx` 用过再说。**

**C3. 真实案例文档** ✅ 部分完成

[`case-study.md`](./case-study.md) 已经写了第一次真实语料验证。

但下一份**更有说服力的案例**需要外部使用者才能产生：

> "接入时基线有 40 条，三个月后降到 12 条，其中 3 条是 CI 挡下来的真实断链。"

**采纳证据比功能更能让人愿意试。** 这份只能等。

### D. 明确不做

| 不做 | 让给谁 | 理由 |
|---|---|---|
| 交互式可视化（缩放/搜索/拖拽） | Quartz / Obsidian | 那条路必败，且**不满足筛子任何一条** |
| 全站 HTTP 链接爬取 | lychee / linkinator | 成熟对手，且不是本项目的差异点 |
| 编辑器插件 | Foam / Obsidian | 绑定编辑器，与"框架无关"的定位冲突 |
| 全文搜索 / 索引 | pagefind 等 | 另一个问题域 |

**判断标准**：一个方向如果既不减少静默错误，也不能提高被调用频率，那它就是"因为能做所以做"。

## 三、冻结前只做一件事

**A5 规则可配置。**

检查项现在有 **10 条**（其中 6 条是错误级）。规则一多，两个问题就浮出来了：

1. **不是每条规则都适合每个项目。** 一个纯 spec 仓库可能完全不关心标签；一个博客可能不关心 frontmatter 必填字段。
2. **不可配置时，用户的唯一选择是关掉整个门禁。** 而那正是本项目花最大力气避免的结局——基线机制、宁可漏报不可误报，都在为"让门禁活着"服务，结果却可能因为"有一条规则不适合我"而前功尽弃。

所以 A5 服务的是**同一个目标**（门禁要活下去），只是从另一个方向：基线解决"历史债太多"，配置解决"规则不适用"。

做完 A5，宣布功能冻结。理由见[第零节](#零完工定义与停止规则)。

### 已完成的补记

A1（行号定位）、A2（基线清理）、A3（图片与本地路径）、A4（无 frontmatter 语料）都已完成。

其中 **A3 与 A4 都不在原始计划里**，各自验证了一条经验：

- **A3 是真实语料撞出来的。** 自己造的示例永远跑不出自己想不到的情况。
- **A4 是回答"什么时候算完"时顺手发现的。** 它差点让整个定位变成假的——工具无法在它声称要服务的主要场景上运行。

**A4 尤其值得记**：它不满足"功能请求"的形态（没人提过），而是一个**让既有宣称成立的前提**。这提示了一条冻结前的检查动作：

> 冻结之前，先验证"README 里声称的每个场景，工具是否真的跑得起来"。

如果只检查功能列表，这个前提永远不会被发现——因为每一条功能都"在"，只是合起来到不了目标场景。

顺带一个结果：现在工具能检查自己的 `docs/`，**4 篇文章 / 4 条互相引用的边 / 0 错误 0 警告**，并且这一步进了 CI。

而 [真实语料验证](./case-study.md) 给出的那个发现仍然成立——**那份 33 篇的博客，文章之间零内部引用**。这是路线图上任何一项都不会告诉你的东西。
