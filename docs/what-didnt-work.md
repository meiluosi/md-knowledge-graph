# 踩过的坑

这份文档记录 md-knowledge-graph 开发过程中**实际踩过**的坑和实测数据。
README 只留摘要，细节在这里。

写作原则：只写真实发生过的。有测试的贴测试，有数据的贴数据。

---

## 1. 手写 frontmatter 解析器会静默丢数据

本工具的前身是一个 51 行的、零依赖的手写 YAML 子集解析器。

逻辑是：遇到 `key:` 空值就进入数组模式，逐行收 `- ` 项；只有 `title` / `category` 被当作标量处理。

它在我自己的 33 篇文章上**从未出错**——因为那些文章恰好全用了块式数组。换几种同样合法的写法，实测结果：

| frontmatter 写法 | 手写解析器结果 | |
|---|---|---|
| `tags:\n  - A\n  - B` | `["A", "B"]` | ✅ |
| `tags: [A, B]` | `[]` | ❌ **静默丢数据** |
| `tags: A` | `[]` | ❌ **静默丢数据** |
| `title: "X: Y"` | `"X: Y"` | ✅ |

问题不在实现粗糙，而在**缺陷形态**：

> 它对非法输入不报错，对合法输入也照样返回空数组。

使用者拿到的是一张少了文章、却不报任何错的图。这类"静默数据丢失"是数据工具最不该有的缺陷。

**所以本项目引入了唯一的依赖 `gray-matter`。** 不是偷懒——是承认「自己维护一个 YAML 子集」的边界成本远高于一个成熟依赖。

上面三种写法现在是三条回归测试（`test/graph.test.js` 的 `normalizeList` 组）。

## 2. 同一概念的两种写法会产出「畸形图」，不是「多一个节点」

实现标签节点时按原写法直接建节点，于是 `PEFT` 和 `peft` 产生了**两个 id 完全相同、label 不同的节点**：

```
tag:peft("PEFT")
tag:peft("peft")     ← 同一个 id 出现两次
```

这不是"图上多一个点"那么轻——它破坏了图的完整性：

- Mermaid 里是重复定义
- 前端按 id 建索引会**互相覆盖**
- 下游拿到的边指向哪个节点，取决于遍历顺序

修复方式是按 slug 归并（`aggregateBySlug`）：

- 计数口径改为「多少篇文章用了这个概念」，同一篇里写两种拼写只算一次
- 规范写法按**多数决**选出
- 票数并列时优先大写更多的那个（`PEFT` 优于 `peft`）

回归测试在 `test/graph.test.js` 的「同概念不同写法的归并」组。

### 附带教训：检查和出图必须共用同一套归并逻辑

最初检查器按原写法统计，于是它**一边警告"会被合并成同一个节点"，一边又按两种拼写各报了一次**——警告本身是错的。

工具内部两处对同一概念有两种口径，是比 bug 更麻烦的问题：它让用户没法信任任何一处输出。

## 3. 代码块里的示例链接会被当成真断链

技术文章里经常出现这种内容：

````markdown
参考 [示例](not-a-real-post.md) 的写法
````

第一版直接对全文做正则，于是所有**文档示例**都成了断链，一篇文章能报出十几条假错误。

现在解析前会剥掉围栏代码块、波浪号代码块、行内代码和 HTML 注释（`stripCode`），只解析真正的正文链接。

验证方式是在示例语料里**故意放一个假链接**：

```
$ mdkg --posts examples --check
✗ 正文断链 —— 1 项
    2026-01-08-qlora-4bit → ./2026-01-01-deleted-draft.md
```

只报出一条——代码块里的 `not-a-real-post.md` 和行内代码里的 `also-fake.md` 都没有被误报。

## 4. wikilink 曾经永远连不上

`resolveTarget` 最初只做路径解析：

```js
path.join(path.dirname(from.id), target)
```

这对 `./a.md` 有效，但 `[[thing]]` 这种不带路径的目标**永远解析不出结果**。

也就是说：功能看起来实现了，测试也"通过"了（因为没有测试覆盖它），**实际一条边都没产生**。

修复时加了一层"无斜杠目标按文件名查找"的回退，但有一个有意的限制：

> 这层回退**只对不含 `/` 的目标启用**。

否则 `./gone.md` 会因为别处恰好有个 `gone` 而被误判成有效链接，**把真正的断链掩盖掉**——这是检查器最不该做的事。

宁可漏报（判为断链）也不能误报（把断链说成好的）。

## 5. 我的测试断言写错过两次，而且两次都该先怀疑测试

**第一次**（`buildGraph`）：我断言"有分类但标签全被过滤的文章仍应入图"。

```
✖ 有分类但标签全被过滤的文章仍然入图
  AssertionError: 文章 c 应通过分类连入图
```

但我构造的数据里那篇文章的 `category` 是空字符串——它本来就该被排除。**是断言错了，不是代码错了。**

**第二次**（`computeRelated`）：`minScore: 3` 时分数恰好是 3，阈值是闭区间、应该保留，我却断言成排除。

两次都差点让我去改一个本来正确的实现。所以：

> **测试失败时，先怀疑测试。**

## 6. 一个拼写事故：`Set.set` 不是 `Set.add`

写标签大小写检查时用了：

```js
bySlug.get(key).set(name);   // Set 没有 set 方法
```

冒烟测试立刻炸了：

```
错误：bySlug.get(...).set is not a function
```

教训很小但很实际：**第一版跑起来看一眼，比读三遍代码便宜。**

补充一句：这个 bug 单元测试当时抓不到——因为那部分测试还没写。是"跑一下看看"抓到的。

## 7. 生成物也需要被测试

`--format html` 的输出是 HTML。**语法正确不代表能跑。**

一个 NaN 坐标、一个漏掉的 canvas 方法，用户拿到的就是一张白屏，而只做语法检查的 CI 抓不到。

`test/html-runtime.test.js` 因此搭了一个最小 DOM stub，把内嵌脚本**真正执行一遍**，断言：

- 每个节点都被绘制（`arc` 调用次数 == 节点数）
- 所有坐标都是有限值（没有 NaN / Infinity）
- 画布按 DPR 正确放大

`test/cli.test.js` 同理。**退出码是 CI 唯一真正依赖的契约**——单元测试全绿但退出码错了，CI 依然是坏的。所以以子进程方式真正把命令跑起来，断言退出码与输出。

## 8. 一个函数被两处复用，产生了整类误报

提取标题锚点时，我直接复用了为**链接提取**写的 `stripCode`。它的行为是「把代码块和行内代码**内容整段删掉**」。

对链接这是对的：

```markdown
参考 [示例](not-a-real-post.md) 的写法     ← 代码块里的假链接，必须删掉
```

但对标题这是错的：

```markdown
## Use `foo` here
```

GitHub 渲染这个标题得到文字 `Use foo here`，锚点是 **`use-foo-here`**。而行内代码被整段删掉后，我的实现算出的是 **`use-here`**。

后果不是"少报"，而是**把正确链接报成失效锚点**——每一篇标题里带行内代码的文档都会炸。

### 这是怎么被发现的

不是我读代码看出来的，是写测试时对照 `github-slugger` 的**实际输出**发现的：

```
✖ "## Use `foo` here" → use-foo-here
```

我把期望值定成 `use-foo-here`（因为那是渲染器的真实行为），实现给出 `use-here`，测试立刻红了。

**这条说明为什么"参考实现的实测输出"比"我以为的规则"更值得当期望值写进测试。**

### 修法

拆成两个语义不同的函数，并在模块文档里写清什么时候用哪个：

| 场景 | 函数 | 行为 |
|---|---|---|
| 提取链接 | `stripCode` | 行内代码**连内容**一起去掉 |
| 提取标题 | `unwrapInlineCode` | 只去反引号，**保留内容** |

教训：**一个"没错"的工具函数被复用到语义不同的场景，本身就能制造整类误报。** 名字里带 `strip` 的函数，复用时要想清楚"剥掉的东西是不是对方需要的"。

## 9. `C:` 被当成了 URL 协议，漏报 19 条

这个 bug 是**在真实语料上跑出来的**，自己在 `examples/` 里永远撞不到。

```js
// 修理前
export function isExternal(target) {
	return /^[a-zA-Z][a-zA-Z0-9+.-]*:/.test(target) || target.startsWith("//");
}
```

`C:\Users\...\a.png` 里的 `C:` 匹配了"协议 + 冒号"的模式，于是整条路径被判为**外链**、直接跳过。

后果：一份 33 篇、19,673 行的真实博客，工具报告 **0 错误**——而它里面有 **19 个 Windows 本机路径引用**，在网页上全部必然 404。

### 为什么这条比第 8 条更值得记

它是**漏报**，而本项目的设计原则是"宁可漏报不可误报"。按这个原则，漏报的危害等级更低。

但它有一个更糟的性质：

> **它让工具对着一批坏引用说"没问题"。**

工具存在的全部理由是把静默错误变成非零退出码。一个静默漏报的工具，是在**替静默错误背书**——那比没有工具更坏，因为它给了虚假的安心。

### 修法

按 RFC 3986，真正的 URI scheme **至少两个字符**。单字母加冒号只可能是盘符。所以顺序要反过来：先判本地路径，再判外链。

```js
export function isLocalFilePath(target) {
	const t = String(target ?? "");
	return /^[a-zA-Z]:[\\/]/.test(t) || t.startsWith("\\\\");
}

export function isExternal(target) {
	const t = String(target ?? "");
	if (isLocalFilePath(t)) return false;   // ← 先判掉
	return /^[a-zA-Z][a-zA-Z0-9+.-]*:/.test(t) || t.startsWith("//");
}
```

### 顺带暴露的第二个漏报

那 19 条全是 `![...]` ——**图片**。而图片原先在提取阶段就被 `!` 前缀过滤掉了，完全不检查。

所以即使修好 `isExternal`，图片仍然是漏报的。两个问题叠在一起，才解释了"0 错误"。

现在图片会被提取（`kind: "image"`）、检查存在性，但**不进入图边**——图片是资源，不是知识结构。

并且新增了 `--asset-root`：站点绝对路径（`/img/...`）单看 markdown 无法判断，只能让用户指定静态资源根目录。不给就不判——**判不了的事不能当成"缺失"**。

## 10. 计数型检查让测试夹具非常脆（我在这上面栽了五次）

`singleton-tag` 这条检查依赖标签出现次数。于是每次我在夹具里"加一篇文章"，都可能顺带改变计数、让某条警告消失。

我因此写错了五次断言，其中四次是同一形态：

```
# 想测：插入无关文章后基线仍然有效
# 实际：插入的文章带了 x、y 标签，把那两条长尾标签警告**真的解决了**
#       → 基线确实应该变化 → "指纹失效"的断言是错的
```

| 次数 | 场景 |
|---|---|
| 1 | `buildGraph`：断言"有分类的文章应入图"，但夹具里那篇的 category 是空串 |
| 2 | `computeRelated`：`minScore: 3` 时分数恰好是 3，闭区间应保留，我断言成排除 |
| 3 | 基线指纹稳定性：同第 5 次 |
| 4 | GitHub 注解：断言"已知 1 项"，实际那份语料有 3 条问题 |
| 5 | `pruneBaseline`：同第 3 次（在新模块里又犯一遍） |

### 教训

**写依赖计数的检查时，测试夹具必须先把计数稳定下来**，再测别的性质。

修法是给这类测试专用一份"标签已达阈值"的语料：

```js
const STABLE_BROKEN = [
  { id: "a", tags: ["x", "y"], category: "C", content: "[没了](./gone.md)" },
  { id: "b", tags: ["x", "y"], category: "C", content: "" },
];  // x、y 各出现两次 → 不再是长尾 → 加文章也不会改变警告集合
```

这样"指纹是否稳定"和"问题本身是否消失"这两件事才能分开测。

### 一个更普遍的观察

这也是**误报敏感的检查器的共同弱点**：凡是"计数型"规则（长尾标签、重复内容、孤儿节点），都会让"加一点东西"产生连锁反应。设计这类规则时就要预期到——它的测试不能像布尔规则那样随手搭夹具。

## 11. 工具在它声称要服务的主要场景上根本跑不起来

这条不是代码 bug，是**定位 bug**，而且差一点就一直存在下去。

### 怎么发现的

在回答"这个项目演进到什么时候算完"时，我顺手用工具检查它自己的文档：

```
$ mdkg --posts docs --check
错误：在 .../docs 里没有找到带 title 的 markdown 文件。
```

**工具无法在纯 markdown 上运行。**

而它的存在理由写在 README 第一段：

> 规格驱动开发把 markdown 从"产物"变成了"接口"……规格文档最常见的失效是**章节被改名，引用还指着旧锚点**。

而 `design.md` / `tasks.md` / `requirements.md` 这类文件**通常没有 frontmatter**——早先的实现要求有 `title`，否则跳过整个文件，于是对着一整个 spec 仓库，它的结论是"没有找到任何 markdown"。

**它无法服务它声称存在的理由。**

### 为什么这条值得单独记

前 10 条都是"实现不符合预期"。这一条是**预期本身没有被验证**：

- 每一条功能都"在"——锚点校验在、链接解析在、退出码在
- 单元测试全绿，257 条
- CI 全绿
- 但它到不了目标场景

而且它**不满足"功能请求"的形态**：没人提过、没有 issue、没有失败案例。它是被一个完全无关的问题（"什么时候算完"）顺手带出来的。

### 修法

标题按 `frontmatter.title → 第一个 H1 → 文件名` 兜底，并且区分两类文件：

| | 含义 | 行为 |
|---|---|---|
| 有 frontmatter | 作者在用这套机制 | 没写 `title` → 警告；没写 `tags` → 警告 |
| 没有 frontmatter | 规格文档、普通文档 | **不产生逐篇的无标签噪声**（它们本来就不用标签） |

第二条很关键。如果对纯 markdown 语料逐篇报"无标签"，一篇 50 个文件的 spec 仓库会得到 50 条噪声——**而噪声会掩盖真正的问题**，那正是本项目一直警惕的误报。

修复后，工具检查自己的 `docs/`：4 篇文章、4 条互相引用的边、0 错误 0 警告。

### 由此得到一条冻结前的检查动作

> **冻结之前，先验证"README 里声称的每个场景，工具是否真的跑得起来"。**

只检查功能列表是发现不了的——每一条功能都"在"，只是合起来到不了目标场景。

这和第 8、9 条是同一类问题的不同层次：那条是**函数**用错了地方，这条是**整套功能**装在了没有预期的场景上。
