# 该不该自己造这个工具

> 一套用来判断「这个能力应该自己写、还是应该找一个现成的」的判据。
>
> 它起源于一个真实问题：写完 md-knowledge-graph 之后，我需要回答它到底有没有存在价值。
> 这套筛子是我当时的判据，也是后来决定继续投入的理由。

---

## 一、为什么这个问题现在才变得重要

「不要重复造轮子」是一句古老的废话。真正难的是判断**什么时候你确实在造轮子**——因为大部分自建工具的开销不在写的那一次，而在：

- 它悄悄错了而你信了
- 每个人各写一份，行为不一致
- 换个人接手时，没人知道该信哪个版本

这个问题在 2026 年变得尖锐，原因是**规格驱动开发（spec-driven development）把 markdown 从「产物」变成了「接口」**。

以前的 markdown 是给人看的文档，写错了顶多没人读。现在的 markdown 是 agent 的输入：需求、设计、任务清单、`AGENTS.md`、记忆文件。**它是程序的一部分。** 程序的一部分就应当有和代码同等的完整性保障——而代码有 `tsc`、`eslint`、CI，markdown 什么都没有。

于是 markdown 的修改频率在上升，而它的正确性没有任何工具在守。这就是这类工具的窗口。

但这不意味着"只要和 markdown 有关就该造工具"。需要筛子。

---

## 二、三条筛子

判断一个能力该不该做成独立工具，问三个问题。**三条都成立才成立**；缺一条就要想清楚缺的那条怎么补。

### 条件 ①：会被高频需要吗

低频需求不值得单独存在——自己写一次就行，哪怕写得糙。

**关键是要看清「谁」在需要，以及频率从哪来。** 这里有个容易搞错的地方：**高频需求往往不来自"主动调用"，而来自"流程强制"。**

没人会主动跑 `eslint`。是 commit hook 和 CI 在跑。所以：

> **条件 ① 的真正问题不是「有人会想起来用它吗」，而是「它能不能被挂进一个必经流程」。**

一个需要用户主动想起来才会跑的工具，实际频率约等于零，无论它多有用。

### 条件 ②：自己写会悄悄错吗

**这是三条里最重要的一条。**

要区分两种错误：

| | 表现 | 后果 |
|---|---|---|
| **崩溃型** | 抛异常、报错退出 | 你立刻知道要修，**自建完全可接受** |
| **静默型** | 返回一个看起来正常的结果 | 你信了，错误往下游传播 |

自建工具的真正风险全在第二类。而**静默错误的典型形态是**：

- 解析失败了，但返回空集合而不是报错
- 边界情况走了默认分支，产出了一个"合法但错"的值
- 功能实现了，但因为某个条件永不满足，**实际一次都没生效**

第三种最阴险：代码在、测试在、看起来在工作，**实际上没有任何输出**。它同时骗过了作者、审阅者和测试。

所以条件 ② 的判据是：

> **把"自己写会错"具体化为"自己写会以什么方式静默地错"。**
> 列不出来，说明条件 ② 不成立；能列出来，这些就是工具的核心测试用例。

### 条件 ③：找到它比自己写便宜吗

注意这条**不只是"用它便宜"**，而是"找到 + 评估 + 采用"的总成本低于自建。它包含三个隐藏成本：

- **发现成本**：别人找得到吗？（独立 CLI 在这条上天然吃亏——它没有上游，不是插件也不是库，没人会路过它）
- **信任成本**：怎么知道它靠谱？——README、测试、CI 徽章的真正作用在这里
- **供应链成本**：多一个依赖意味着多一个可能被弃维护、被投毒、被破坏性升级的东西

第三条常常被低估。一个 3000 行、零依赖、逻辑只做一件窄事的自建脚本，在某些场景下确实优于引入一个 50 个传递依赖的成熟库。**"成熟"本身也是有价格的。**

## 三、关键不对称：条件 ② 买不到，条件 ① 可以买

这是整套筛子里我最想强调的一点。

- **条件 ① 是可以被"制造"的。** 你把工具挂进 CI、做成 pre-commit hook、写进项目模板，调用频率就被流程保证了。**这不需要说服任何人高频想起它。**
- **条件 ② 是买不到的。** 它是问题本身的性质，跟你怎么包装、怎么推广完全无关。一个会静默出错的问题，无论被多好地集成，都仍然会静默出错。

由此得到一条策略：

> **把叙事压在条件 ② 上（因为那是不可替代的），用集成把条件 ① 买回来（因为那是可以补的）。**

并且在资源有限时，**优先投入到"减少静默错误"上**，而不是"增加调用频率"上。前者是护城河，后者是运营。

### 推论：工具的价值可以写成一句话

如果一个能力满足条件 ②，它的价值主张可以精确表述为：

> **把一类静默错误，转变成一条明确的、非零的退出码。**

这句话比"帮你检查 XXX"有力得多，因为它说明了**没有它的时候，代价具体是什么**。

## 四、我建议补的两条

原三条筛的是**收益**。下面两条筛的是**为什么工具会被弃用**——这是不同的失败模式。

### 条件 ④：误报率可控吗

一个检查类工具最常见的死法不是漏报，而是**误报**：

> 一开就红 → 用户发现里面有两条是假问题 → 用户不再信任它 → 用户把它关掉。

误报会摧毁条件 ①：门禁一旦被关，调用频率归零。

**推论一**：误报和漏报不对称。**宁可漏报，不可误报。**

这在实现层有直接对应。两个真实例子：

**例一（解析歧义）**：解析链接时，如果目标文件名有歧义（两个不同目录下有同名文件），正确做法是返回"解析不出"——即**报为断链**，而不是猜一个。猜错会把真断链掩盖掉，那是检查器最不该做的事。

**例二（函数被误复用）**：为链接提取写的 `stripCode` 会把行内代码**内容整段删掉**；把它复用到标题提取上，标题 `` ## Use `foo` here `` 算出的锚点就成了 `use-here`，而渲染器给出的真实锚点是 `use-foo-here`。于是**每一篇标题里带行内代码的文档，所有指向它的链接都被报成"失效锚点"**。

第二个例子的可怕之处在于：复用的那个函数**本身没有任何 bug**。是"它对，但用错地方"产生了整类误报。这类问题读代码看不出来，只能靠拿参考实现的实测输出当期望值来测。

**推论二**：门禁必须支持基线。

> 第一次接入时，历史问题会一次性全部报出来 → CI 永远红 → 门禁被关掉。

正确设计是记录一份基线，**只对新增问题失败**。这是让门禁能长期存活的必要条件，而不是一个可选功能。

### 条件 ⑤：依赖成本确实低于自建吗

不是"能不能引依赖"，而是"引了之后总成本更低吗"。

一个可操作的判据：**如果引入依赖的理由是"我自己维护这套逻辑的边界成本更高"，那就引；如果理由是"少写点代码"，那再想想。**

真实例子：本项目唯一引入的依赖是一个成熟的 frontmatter 解析库，而它同时砍掉了一个自研的、更轻的解析器。理由不是"省事"，而是**自研那个在合法输入上会静默返回空数组**——即条件 ② 不成立（自建会静默错），所以自建在这个局部是错的。

## 五、走一遍：md-knowledge-graph

用这套筛子评估一个真实项目（判断 markdown 目录的健康度：跨文件引用完整性、标签一致性、相关文章）。

### 打分

| 条件 | 判定 | 依据 |
|---|---|---|
| ① 高频需要 | ⚠️ **弱** | 主动调用不高频。诚实对比：`eslint` / `tsc` 满足，这个不满足——内容编辑频次低于代码编辑 |
| ② 自己写会悄悄错 | ✅ **很强** | 见下方清单，全部为实证 |
| ③ 找到它比自己写便宜 | ✅ 成立，但有前提 | 一行命令确实比自建便宜；**前提是能被找到**，而这是它最弱的一环 |
| ④ 误报率可控 | ⚠️ 需设计 | 代码块里的示例链接、同名文件歧义——都是实测踩到的误报源 |
| ⑤ 依赖成本 | ✅ | 一个依赖，且砍掉自研逻辑有明确理由 |

### 条件 ② 的具体清单（全部来自实际开发）

| 自己写的版本会怎么错 | 错误形态 |
|---|---|
| 手写 frontmatter 解析 | `tags: [A, B]` 与 `tags: A` 解析成 `[]`，**不报错** |
| 同名异写建节点 | 生成两个 **id 相同**的节点，图畸形但**能跑** |
| wikilink 解析 | 实现了、有测试，**实际一条边都没产生** |
| 代码块里的示例链接 | 全部报成断链，一篇文章十几条假错误 |

四个错，**没有一个会崩溃**。全都是"返回了一个看起来正常的结果"。

这就是条件 ② 成立的方式：**不是"自己写会出 bug"（所有代码都有 bug），而是"自己写出的 bug 不会喊叫"。**

### 结论

- 条件 ② 是本项目的存在理由，叙事必须压在它上面。
- 条件 ① 是短板，**用集成补**：CI 模板、Action、pre-commit。让流程去调用它，而不是指望人想起来。
- 条件 ④ 需要显式设计：基线机制 + 宁可漏报不误报。
- **可视化不满足任何一条。** 它好看，但没有 agent 会因为需要图而调用它——那部分是作品价值，不该按工具价值去论证。

## 六、反过来用：什么时候不该造

这套筛子更适合反向提问。以下情形**不该**做成独立工具：

- **崩溃型错误**：错了会立刻报错，自己写就行
- **一次性需求**：跑一次就完，哪怕手写几行
- **已有成熟工具且你的差异只是"我更顺手"**：那是个人偏好，不是价值
- **你的差异是"我不用依赖"**：除非依赖成本高到确有依据，否则这是自我感动
- **低频 + 不崩溃**：两条都不满足，纯粹是自娱
- **没有计划把它挂进任何流程**：条件 ① 基本归零

最后一条最容易被忽略。**一个需要用户主动想起来的工具，等于不存在。**

## 七、速查表

| 问题 | 成立 | 不成立怎么办 |
|---|---|---|
| ① 会被高频需要吗？ | 能挂进必经流程（CI / hook / 模板） | 先解决集成，别急着加功能 |
| ② 自己写会悄悄错吗？ | 能列出具体的静默失效形态 | **不要造**——这是唯一不可替代的一条 |
| ③ 找到它比自己写便宜吗？ | 发现 + 信任 + 供应链成本都低 | 降低采用门槛：一行命令、零配置、可离线 |
| ④ 误报率可控吗？ | 误报可归零或可基线化 | 设计基线机制；宁可漏报不可误报 |
| ⑤ 依赖成本低于自建吗？ | 引依赖的理由是"自研边界成本更高" | 自建，但把静默失效形态写成测试 |

**如果只能记住一句话：**

> 值得做成工具的问题，是那些**做错了不会喊叫**的问题。
