# 真实语料验证

一次在真实项目上跑本工具的完整记录。

**为什么必须做这件事**：`examples/` 是我自己造的，它只能证明"工具在我想得到的情况上是对的"。真实语料会撞出想不到的情况——这次就撞出了一个漏报 bug，以及一个比 bug 更值得记的发现。

## 语料

| | |
|---|---|
| 来源 | 个人技术博客（Astro 站点）的 `src/content/posts` |
| 规模 | **33 篇** · 19,673 行 · 616 KB |
| 形态 | 中文技术长文，frontmatter 用块式数组标签 + 单一 category |
| 导出方式 | `git archive HEAD`（只读，不动工作区） |

选它的理由：**它是我自己的项目**，所以结果可信、可以复盘；而且它规模真实（不是玩具语料），结构上也代表了一类常见博客——写得久、文章多、彼此独立。

## 第一次跑：工具说"干净"

```
$ mdkg --posts src/content/posts --check
⚠ 只出现一次的标签 —— 8 项
错误 0 · 警告 8  → 仅警告，退出码 0
```

**0 错误。** 对一个写了两年的博客来说，这个结果值得高兴——但值得先怀疑一下。

我没有直接接受它，而是问了一句：**"干净"是真的没有引用问题，还是工具根本没看到引用？**

查下去发现是后者：

```
linksFound: 0        ← 内部链接总数
linkEdges : 0
```

可是语料里明明有 118 个 markdown 链接。逐个看下去，找到了：

```
C:\Users\11603\OneDrive\实习准备\assets\image-20240524171840913.png
C:\Users\11603\OneDrive\个人项目\因果推断学习\工具学习\R语言学习\assets\image-20240915213959756.png
```

**19 个引用写成了 Windows 本机路径。** 这在网页上必然 404——它们全都指向只存在于我电脑上的文件。

### 根因

```js
// 修理前
export function isExternal(target) {
  return /^[a-zA-Z][a-zA-Z0-9+.-]*:/.test(target) || target.startsWith("//");
}
```

`C:` 匹配"协议 + 冒号"的模式，于是整条路径被判定为**外链**，直接跳过。

按 RFC 3986，真正的 URI scheme **至少两个字符**——单字母加冒号只可能是盘符。这个区分当时没想到。

### 为什么这个 bug 特别值得记

它是**漏报**，不是误报。按本项目的设计原则（宁可漏报不可误报），漏报的危害等级更低——但它有个更糟的性质：

> **它让工具对着一批坏引用说"没问题"。**

而工具存在的全部理由，就是把静默错误变成非零退出码。一个静默漏报的工具，是在**替静默错误背书**。

这个 bug 在我自己造的 `examples/` 里永远跑不出来——因为我想不到要写 `C:\...`。

## 修好之后

```
$ mdkg --posts src/content/posts --check
✗ 本地文件系统路径（在网页上必然打不开） —— 19 项
    2024-06-09-关于数据分析思考:129  →  C:\Users\...\image-20240522194214888.png  (image)
    2024-06-09-关于数据分析思考:135  →  C:\Users\...\image-20240524170101290.png  (image)
    …
错误 19 · 警告 8  → 存在错误，退出码 1
```

**从 0 到 19**，而且每条都带精确行号，两份文件里各在哪些行一目了然。

修复本身很小：本地路径要在 `isExternal` 之前判掉。但顺带补了两件事：

1. **图片引用纳入检查**。这 19 条全是 `![...]`——即使修好了 `isExternal`，图片原先也是完全不检查的，所以仍是漏报。
2. **本地路径与断链分开归类**。它们的修复动作不同：断链是"路径写错了"，本地路径是"资源没上传"。混在一起会给出错误的修复指引。

## 比 bug 更值得记的发现

数据里有这么一行：

```
post↔post 引用边: 0
```

**33 篇文章，彼此之间一条引用都没有。**

这个博客有标签、有分类、有 68 条归属边——看起来结构完整。但把标签层拿掉，剩下的就是 33 个互不相连的点。

这正是 README 里说的那件事：没有 `post↔post` 边，图谱只是标签浏览器。而**一个真实的、写得挺认真的技术博客，恰好就是这种情况**。

它不一定是"错"——很多博客就是这样写的，一篇一个主题，写完就发。但值得知道：

- 读者读完一篇，没有"下一篇读什么"的线索
- 搜索引擎看到的是 33 篇孤立文档，而不是一个互相印证的知识网络
- 标签只能表达"同类"，不能表达"前置知识"、"后面会用到"、"这是那个结论的出处"

**这是这次真实语料验证里最有价值的产出，而且它不是工具的功能问题，是关于被检对象的事实。**

## 顺带看到的两件事

### 标签结构：15 个标签，8 个是长尾

```
⚠ 只出现一次的标签 —— 8 项
    工程实践 / 推理优化 / 大模型训练 / LLM全链路 / MLX / QLoRA / Apple Silicon / 实验计划
```

33 篇文章用了 15 个标签，其中 8 个只出现一次。默认 `--min-tag-count 2` 会把它们挡在图外——剩下 7 个标签撑起整张图。

长尾标签不一定是坏事（`QLoRA`、`Apple Silicon` 都很具体），但当一半以上的标签只用一次时，标签体系实际上**没有起到聚类作用**。

### 零引用下，相关文章仍然算得出来

```
33 篇中有 33 篇算出了相关文章

2024-06-09-关于数据分析思考
   → 2024-08-15-统计学基础与假设检验   (score 3, category:Data Science, tag:数据处理)
   → 2024-6-30-数据分析实战—Dowhy…     (score 3, category:Data Science, tag:数据处理)
```

这是 `--format related` 的实际价值：**即使作者一条引用都没写，标签与分类的重叠仍能给出可用的"相关阅读"**。

它同时暴露了这条路的局限——上面三条的分数完全一样（都是 category + 一个共享标签），因为输入信号就只有这些。**信号越少，排序越没有区分度。** 想让"相关阅读"真正好用，还是得靠正文引用。

## 性能

| | |
|---|---|
| 33 篇 / 19,673 行 | **0.064 秒** |

对 pre-commit 钩子来说完全够用。真正的规模问题要等到几千篇才会出现（见 [`roadmap.md`](./roadmap.md) 的 B3）。

## 这次验证带出的改进

| 改动 | 依据 |
|---|---|
| 修 `isExternal`：单字母 + 冒号是盘符，不是协议 | 19 个引用的漏报 |
| 图片引用纳入检查 | 那 19 条全是图片，原先完全不看 |
| 新增 `local-file-path` 检查项 | 与"断链"的修复动作不同，不该混为一类 |
| 新增 `--asset-root` | 站点绝对路径（`/img/...`）无法判断，只能靠用户指定资源根目录 |
| 示例语料补上本地路径与缺失图片 | 否则这两个能力在演示里看不见 |

## 结论

三条经验，写在 `when-to-build-a-tool.md` 里的判据之外的：

1. **"0 错误"要先怀疑，再采信。** 尤其当被检语料是真实的、你并不完全了解它的时候。工具的"没问题"和"没看到"在输出上长得一样。
2. **自己造的示例永远跑不出自己想不到的情况。** 这一整节的内容，没有一个能靠扩充 `examples/` 得到。
3. **真实语料最大的产出往往不是 bug，是关于被检对象的事实**——"33 篇文章零内部引用"比"修好了一个正则"重要得多。

下一步打算把这个博客的基线建立起来（19 项本地路径进入基线，不再阻塞），然后逐篇补上正文引用——那时 `post↔post` 边就会从 0 开始增长，`related` 的排序也会真正有区分度。
